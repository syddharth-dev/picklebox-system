# Security audit and remediation

Report date: November 1, 2026, Asia/Manila. Scope: the repository's frontend, Supabase API/RPC functions, database policies and grants, all three Edge Functions, admin authorization boundaries, exports, dependency lockfile, and development/production configuration.

**The fixes are implemented locally. No hosted database migration, Edge Function deployment, production-header change, credential rotation, booking mutation or load attack was performed.** Hosted configuration and schema drift remain deployment checks, not verified facts. This is a source and isolated-regression audit, not a guarantee that every possible vulnerability has been discovered.

## Confirmed findings and fixes

| ID | Severity | Finding and impact | Implemented solution |
| --- | --- | --- | --- |
| S01 | Critical to low, as reported by npm | The initial dependency audit reported 31 affected packages: 1 critical, 6 high, 23 moderate and 1 low. These are dependency advisories, not 31 demonstrated application exploits. | Updated compatible dependencies, upgraded ESLint and its compatible plugins, replaced vulnerable transitive minimatch/CSS parser versions through overrides, and removed unused `@lovable.dev/mcp-js` and its dependency tree. The final npm audit reports **0 vulnerabilities**. Production build and feature tests exercise the updated tree. |
| S02 | Medium | `get_reserved_slots` returned staff-entered `admin_note` text to any authenticated caller. Internal notes can contain private operational/customer information. | The RPC returns notes only to admins, retaining minimal court/hour availability for players. The old SQL fails the note-masking regression; the new migration passes it under actual SQL roles. |
| S03 | Medium | A player could submit many pending bookings with arbitrary references, occupying future inventory without verified payment. Pending holds have no automatic expiry in this product. | A database trigger serializes same-account hold checks and caps future pending holds at **24 court hours**. Persistent quotas permit up to **30 booking rows per minute** and **20 Open Play registrations per minute**, including cancellation/rebooking cycles. Limits apply to API calls, not just UI clicks. Checkout/Open Play display useful limit messages. Admin workflows are exempt from the player trigger. |
| S04 | Medium | Edge Functions parsed entire request bodies before bounding their actual byte size. Chat lacked an explicit output-token budget, provider-response bound, request timeout and daily per-account cost limit. | A shared streaming JSON reader caps chat bodies at **64 KiB** and notification bodies at **2 KiB**, even with a forged/missing Content-Length, and times out body reads after **5 seconds**. Chat limits history to **12,000 characters**, output to **512 tokens**, gateway time to **25 seconds**, provider JSON to **64 KiB**, returned text to **8,000 characters**, and usage to **10 requests/minute plus 100 per 24-hour window per account**. |
| S05 | Medium | Notification requests used a service-role booking lookup before ownership checks. Different 403/404 responses revealed whether a guessed booking ID existed. Successful requests fetched/logged the recipient's email even though email delivery is unimplemented. There was no endpoint quota. | Fetch through the caller's RLS-scoped client, validate UUID/type, return identical 404 responses for absent/inaccessible records, and apply a persistent **20 requests/minute/account** quota. Removed service-role/auth-directory access and customer-address/reference logging from this endpoint. It still honestly reports `emailSent: false`. |
| S06 | Medium | CSV quoting did not neutralize spreadsheet formulas in untrusted names, phone numbers or other exported text. A player-controlled cell beginning with `=`, `+`, `-` or `@` could be interpreted as a formula when staff opened the export. | Prefix dangerous cells with a text apostrophe before CSV escaping, including leading whitespace/control-character variants. Quotes, commas and carriage returns are escaped. Numeric-looking phone strings retain their text value. Formula-execution behavior was not exercised in a real spreadsheet application. |

Severity reflects plausible impact in this application. S03/S04 controls reduce abuse; multi-account attacks still require hosted signup controls and provider-level budgets.

## Additional hardening

- **Retired RPC:** old migrations grant authenticated execution of `create_booking_reservation(uuid,date,time[],text)`, but its implementation is absent from this checkout. The new migration revokes API execution if it exists. No exploit claim is made about an unavailable function body. The current checkout calls `create_bookings_atomic`.
- **Least privilege:** revoke raw `booking_slots` access and expose availability through the narrow RPC. Earlier migration comments describe shared slot reads, but the original slot-table definition is missing; tests explicitly model that legacy policy as a fixture. Confirm the hosted grants with the preflight script. Existing RLS already blocked player role escalation and payment self-approval; the audit tests verify these protections rather than claiming they were newly discovered bypasses.
- **Database defaults:** API roles cannot create objects in `public`. New functions/tables created by the migration owner no longer receive automatic API access; new functions require explicit grants. Definer functions explicitly put `pg_temp` after trusted schemas. Other migration owners/roles need the same default-privilege policy.
- **Profile integrity:** owners can update only `full_name`, `phone` and `avatar_url`; auth triggers create profiles. Identity/timestamps cannot be replaced through profile updates. Database byte-size constraints bound profile values. New/updated court prices, booking totals and payment amounts must be nonnegative and not NaN. `NOT VALID` constraints protect new writes without rewriting historical data.
- **Endpoint boundaries:** current Auth-server user verification is required; Edge Function clients disable session persistence/refresh. All imports pin Supabase JS to `2.93.3`. Cleanup requires POST and rejects browser-origin requests before writes, while retaining service-role/admin authorization. Its response returns a count rather than booking identifiers. Existing `verify_jwt = true` settings remain enabled.
- **Response privacy:** authenticated function responses use `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Vary: Origin`. Provider error bodies and customer notification contents are not logged. Exact CORS origin allowlists remain required; CORS is not a substitute for authentication or authorization.
- **Production headers:** `public/_headers` provides CSP, frame protection, nosniff, referrer/permissions policy and HSTS for hosts supporting this format. The CSP permits the actual next-themes bootstrap by SHA-256 rather than allowing arbitrary inline scripts. It allows the existing Google fonts, Supabase HTTPS/WebSocket traffic and camera-based scanner. Other hosts must configure equivalent HTTP headers; copying this file alone does not prove enforcement.
- **Development exposure:** Vite now binds to loopback, uses a fixed port and denies environment files, keys, Git metadata, agent files, diagnostics and backend source. Restart any already-running dev server to use the updated Vite/version/configuration.
- **Local configuration/lockfiles:** moved the tracked public-only `.env` to ignored `.env.local` so future credentials are not added to that tracked path. No service-role or provider secret was found there; VITE variables are public browser configuration. npm's updated lockfile is authoritative; the stale Bun lock is preserved outside the install root at `.design/security-legacy-bun.lockb`. Use `npm ci` for reproducible installs.

## Verification

Final verification: **229 tests across 29 files pass**, including the existing admin tests, using `npm test -- --reporter=dot --maxWorkers=2`. Production build, application TypeScript, strict Edge Function source type checks, lint on security-changed files and `git diff --check` pass. `npm audit` reports **0 vulnerabilities** across production and development dependencies.

A concurrent run alongside the build/type/lint jobs hit the default five-second timeout in three UI tests. Running the complete suite alone with two workers passed without increasing test timeouts. The earlier 226-test suite also passed; the final additions cover Open Play SQL-role authorization and friendly limit errors.

- Database regressions use real `anon` and `authenticated` PostgreSQL roles in PGlite and actual application policies/RPC migrations. Coverage includes cross-account booking/payment/profile/roster reads, direct payment/booking forgery, role escalation, protected profile columns, admin-only operations, QR ownership/payment approval, notes, raw slots, legacy RPC access, default privileges, persistent quotas and hold limits.
- Two selected regressions fail against the pre-fix SQL and pass after the migration: staff-note masking and raw-slot access denial. The raw-slot baseline is a documented legacy-policy fixture, not a hosted-schema observation.
- Edge tests execute actual handler source with isolated auth/database/network dependencies. They cover missing/invalid authentication, origin/method rejection, forged Content-Length, oversized and unfinished bodies, conversation/output bounds, quota exhaustion, hidden-vs-missing IDs, status mismatches, cleanup authorization and non-caching responses. No customer message, AI request, outgoing email or real cleanup was sent.
- CSV and CSP bootstrap regressions pass. Strict TypeScript checks cover the application and Edge Function sources; the latter use a small local Deno declaration and installed Supabase types, not a real Deno deployment.
- Secret-pattern scan: **156 reachable Git commits** and **449 unique historical source/configuration blobs**, with no matches for the selected private-key, live-provider-key and Supabase-secret patterns. JWT payloads in those blobs and the current `.env.local` were classified without printing tokens: all five matches had the public `anon` role. This pattern scan cannot prove the absence of every credential format or an external secret. The redacted summary is `.design/security-secret-scan.json`.
- Whole-repository lint still reports **47 errors and 8 warnings**, including existing `any`/scaffold issues and additional hook-rule findings exposed by the updated linter. Security-changed files are checked separately; a zero-vulnerability dependency scan is not a claim that all lint is clean. Production build retains the existing large-bundle/config warnings.

## Deployment and operational checks

1. Use the updated npm lockfile and a compatible Node runtime. Verification used Node **22.20.0** and npm **10.9.3**. Run `npm ci`, the full test suite, TypeScript checks, build and `npm audit` in the deployment pipeline.
2. Run `supabase/diagnostics/security_preflight.sql` in staging as the migration operator. Inspect unexpected public functions, grants, missing RLS and historical invalid data. The repository's older migration history lacks some foundational definitions, including `booking_slots` and the retired RPC; it is not certified for a fresh full Supabase reset. Tests supply explicit fixtures for these gaps, pgcrypto random bytes and platform-only cron behavior.
3. Apply pending migrations in order, including the earlier booking-time guard and `20261031150000_api_security_audit.sql`. The new migration is transactional, preserves records and changes grants/constraints/quotas. New quotas require staging checks using representative multi-item bookings. Historical bad values are not guessed, deleted or corrected; review them before validating `NOT VALID` constraints.
4. Deploy **faq-chat**, **send-booking-notification** and **cleanup-expired-bookings**, including `_shared/http.ts`, after the database migration. Notification/chat quota failures deny requests if their database dependency is missing. Keep JWT verification enabled and set `ALLOWED_ORIGINS` to exact frontend origins. Verify the pinned remote imports in the deployment runtime.
5. Configure the production host's security headers and verify actual responses. `_headers` is a host-specific template; Lovable/other hosting may require a different configuration. Frame denial is intended for production, so trusted editor embedding must be scoped separately if needed. Test theme startup, fonts, Supabase Realtime, camera scanning and PDF export under the enforced policy. HSTS requires HTTPS.
6. Independently verify hosted Auth settings: email confirmation, signup/login rate limits, CAPTCHA where appropriate, leaked-password protection, allowed redirect URLs, admin MFA and session revocation procedures. These dashboard settings were not inspected or changed. Set a hard provider-level AI spend cap; per-account quotas do not defeat unlimited account creation. Restrict service-role keys to trusted backend secrets and rotate any separately known exposed credentials.
7. Repeat the owner/non-owner/admin matrix against staging's actual REST/RPC/Edge endpoints, and verify the policy catalog again after deployment. Review logs for sensitive data and rejected-abuse rates. Multi-connection races, sustained load, physical scanner behavior and external-provider delivery remain unverified here.

The earlier missing real-email integration and historical invalid booking record remain functional/data issues documented in the player/browser audits. This audit does not implement automatic payment verification, alter refund policy or certify GCash settlement.
